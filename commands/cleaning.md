Ты выполняешь команду уборки `/cleaning`. Цель — навести порядок в коде/файлах БЕЗОПАСНО. Код может жить на VPS, локально на ПК/ноуте, или и там и там — СНАЧАЛА определи где (Шаг 0.5), потом действуй по ветке A/B/C.

VPS: `ssh <user>@<your-server>`. Боты: `/path/to/bots/<bot>/` (у каждого свой `venv`). Память: `/path/to/memory/`. Сайты: `/var/www/`. Утилиты диагностики: `/path/to/diagtools/bin/{ruff,vulture,radon,pip-audit,gitleaks,pylint}`.

## ГЛАВНОЕ ПРАВИЛО ОБЩЕНИЯ (не нарушать)
Пользователь НЕ технарь. Запрещено давить терминами и кишками кода.
- Объясняй ЛОГИКОЙ: «этот файл отвечает за X», «эта штука дублирует ту», «меняю А на Б, потому что…», «риск такой-то / рисков нет».
- НЕ «F401 unused import в модуле foo», а «бот подключает библиотеку, которой не пользуется — убрал, чтобы не мусорить».
- Каждый пункт отчёта = четыре вещи простыми словами: ЧТО это · К ЧЕМУ относится · ЧТО меняю · ЧЕМ рискуем (или «рисков нет»).
- Списки — с цифрами, чтобы можно было выбрать номером.

## ШАГ 0.5 — ГДЕ ЖИВЁТ ПРОЕКТ (определить ДО инвентаризации)
Код проекта может быть на VPS, на локальной машине (ПК/ноут) или и там и там. Сначала определи:
- **VPS-часть ЕСТЬ**, если: `ls /path/to/bots/<proj>` непусто, ИЛИ `systemctl` знает сервис, ИЛИ `ps aux` на VPS показывает процесс.
- **Локальная часть ЕСТЬ**, если: локально нашёлся код (Glob `**/<proj>/**/*.py`), ИЛИ на ПК запущен процесс (`Get-CimInstance Win32_Process` по имени/CommandLine).
Итог: только VPS → **ветка A**; только локально → **ветка B**; и там и там → **ветка C**. Объяви пользователю простым языком, какой случай.

### Ветка A — проект на VPS (по умолчанию: work_bot, sell_bot, buh_bot…)
- ГДЕ КОД: `/path/to/bots/<bot>/` + venv бота.
- ДИАГНОСТИКА: прямо на VPS через `/path/to/diagtools/bin/*` или venv бота.
- БЭКАП: git-коммит в папке (если git), иначе `tar` в `/path/to/backups/`.
- СМОУК-ТЕСТ: `systemctl restart <svc>` → `is-active` + `journalctl -n 30`.

### Ветка B — проект локальный (ПК/ноут: напр. stereo_dictate)
- ГДЕ КОД: на машине (напр. `~/YandexDisk/CLAUDE/<proj>/`). На VPS кода НЕТ — только память (+ иногда старые `.bak`).
- ДИАГНОСТИКА: локальных ruff/vulture обычно НЕТ. Упакуй ТОЛЬКО `.py` (`find … -print0 | tar --null -czf` — без моделей/venv/датасетов; на Windows пути с пробелами/кириллицей → ОБЯЗАТЕЛЬНО `-print0` и кавычки) → `scp` на VPS `/tmp/<proj>_diag` → прогон диагтулз → УДАЛИ temp после (особенно если нашёлся секрет). Если ruff/vulture есть локально — можно на месте.
- БЭКАП: git/tar ЛОКАЛЬНО, не на VPS.
- СМОУК-ТЕСТ: процессы запущены руками (foreground), systemctl НЕТ → `py_compile` каждого правленого файла. ЖИВОЙ ПРОЦЕСС НЕ УБИВАТЬ (держит старый код в памяти; правки подхватятся при ручном рестарте — предупреди об этом). Есть HTTP `/health` — пингани.
- РАНТАЙМ-ПРОВЕРКА: `ps`/`Get-CimInstance` — что реально запущено; если движок с моделью — что в VRAM (`nvidia-smi`, `/health`). Отличает «лежит на диске» от «используется» → развязывает руки по сносу дублей.
- ПАМЯТЬ: всё равно пишем на VPS.

### Ветка C — гибрид: и VPS, и локально (напр. work_bot на VPS + dictate_server на ПК через туннель)
- ГДЕ КОД: ОБА. Часть в `/path/to/bots/<bot>/` (VPS), часть локально. Связаны туннелем/HTTP/общим токеном.
- КАРТА: покажи ОБЕ половины + ЛИНИЮ СВЯЗИ (туннель `:порт`, HTTP, общий бот-токен). Предупреди: правка одной половины бьёт по другой (убрал эндпоинт на сервере ПК → отвалилась транскрибация work_bot на VPS).
- ДИАГНОСТИКА: VPS-часть на месте; локальную — упаковать+scp как в B. Прогнать ОБЕ.
- БЭКАП: для КАЖДОЙ половины своя точка (git/tar там, где она живёт).
- СМОУК-ТЕСТ: VPS-часть → systemctl; локальная → py_compile + не убивать; ПЛЮС проверь СВЯЗКУ целиком (тестовое в work_bot → дошло до GPU на ПК → вернулся текст). В гибриде гоняй сквозной путь, а не половинки.
- ПОРЯДОК: по одной половине за раз, между ними — проверка связки.

## ШАГ 1 — ИНВЕНТАРИЗАЦИЯ СЛЕДА (только чтение, ничего не меняем)
Собери ВЕСЬ след объекта по всему VPS, а не только папку бота:
- код: `/path/to/bots/<bot>/`
- сайт/лендинг: `/var/www/*<proj>*`
- сервис: `systemctl cat <svc>` (WorkingDirectory/ExecStart — куда «прибит» код)
- nginx: `/etc/nginx/sites-*/` относящиеся к проекту
- cron: `crontab -l`, `/etc/cron*`
- память: `/path/to/memory/project_<proj>*.md`
- потерянные скрипты: `/root`, `/tmp`, `/opt` вне `bots`
Для режима 0 (вся VPS): ищи НИЧЬИ артефакты — старые бэкап-папки (`*_backup_*`), висячие `*.pid`, забытые `*.log`, выключенные/битые сервисы, дубли каталогов, потерянные файлы в `/root`.

Выдай **КАРТУ ПРОЕКТА** простым языком: «проект живёт так — мозги тут, сайт там, сервис такой, память здесь». Карта — это «собрать в кучу» ЛОГИЧЕСКИ. Файлы, которые куда-то воткнуты (сайт/сервис/настройки), НЕ перемещаем — только описываем.

## ШАГ 2 — ДИАГНОСТИКА (только чтение)
В папке кода (через `venv` бота или утилиты diagtools):
- мусорные подключения и переменные: `/path/to/diagtools/bin/ruff check --select F401,F811,F841 <путь>`
- мёртвый код (с уверенностью): `/path/to/diagtools/bin/vulture <путь> --min-confidence 90` — основной прогон (почти точно мусор). ДОП. информационный прогон `--min-confidence 60` (ловит то, что 90 пропускает — напр. функцию, которая определена, но нигде не вызывается); находки 60 подавать как «возможно мёртвое, проверить», не как факт. ⚠️ ВАЖНО: vulture МАССОВО ложит на функции-ОБРАБОТЧИКИ с декораторами (`@dp.message`, `@router…`, `@app.route`, `@app.get/post`, callback'и aiogram/Flask/FastAPI) — он не видит, что их зовут по событию. Такие «unused function» — НЕ мёртвый код, игнорировать пачкой, к удалению НЕ предлагать
- переусложнённые места: `/path/to/diagtools/bin/radon cc <путь> -nc`
- уязвимые/лишние зависимости: `pip-audit` по `requirements.txt` (если есть)
- дубли файлов: по хешу (`md5sum`/`sha1sum`), и задвоенные имена функций
- дубли КУСКОВ кода (для слияния): `/path/to/diagtools/bin/pylint <путь> --disable=all --enable=duplicate-code`
- утёкшие секреты (токены/пароли/ключи): `/path/to/diagtools/bin/gitleaks detect --source <путь> --no-git -v 2>&1 | sed 's/\x1b\[[0-9;]*m//g'` (sed убирает цветовые ANSI-коды). Это ГЛАВНЫЙ детектор для группы РИСКИ (150+ шаблонов). При находке: НЕ печатать сам секрет, сказать «файл X строка N, тип». ОБЯЗАТЕЛЬНО перепроверь каждую находку глазами — gitleaks ложит на URL/порт/хеш (напр. `...:443/path` принимает за ключ). Реальный риск = ключи/токены прямо в КОДЕ; секреты в `.env` — норма для VPS-деплоя (если `.env` не в git). Если секрет нашёлся ПРЯМО В КОДЕ: проверь `git remote -v` — есть ли публичная выгрузка (нет remote → масштаб утечки мал). И помни: если секрет уже в git-ИСТОРИИ, простой перенос в `.env` его из истории НЕ убирает — нужна РОТАЦИЯ токена. В отчёт (группа D): где, тип, есть ли remote, нужна ли ротация.
- ещё риски: `print(` вместо логгера, `TODO/FIXME`
- хлам: `*.bak`/`*.old` в корне проекта (забытые ручные бэкапы); `logs/` если разрослись; `venv/` под трекингом git. `__pycache__`/`*.pyc` — тоже хлам, НО на работающем сервисе регенерятся после рестарта, толку чистить ноль (см. тривиальные фиксы)

## ШАГ 3 — ОТЧЁТ (человеческим языком, ранжированно)
Раздели находки на 5 групп и по каждой — ЧТО/К ЧЕМУ/ЧТО МЕНЯЮ/РИСК:
- (A) **Сделал сразу** — тривиальные безопасные фиксы (см. ниже), пиши что именно убрал и почему это не ломает.
- (B) **Мёртвый код — кандидаты** — нужен твой ОК (могут быть ложные срабатывания).
- (C) **Дубли / кандидаты на слияние** — что на что похоже, можно ли слить безопасно.
- (D) **РИСКИ** — утёкшие токены/пароли, конфликты имён, битые сервисы. Помечать ярко.
- (E) **Мусор** — что можно снести (висячие pid/логи, старые бэкапы `*.bak`/`*.old`, забытые каталоги). `__pycache__` на живом боте не считать «к сносу» — регенерится. Сюда же — ДУБЛИ КРУПНЫХ ДАННЫХ (модели/веса/кэши) между соседними приложениями (по хешу/размеру папок): кандидат на дедуп через симлинк/общий путь. Это ДАННЫЕ (обычно в `.gitignore`) — чистить ТОЛЬКО с подтверждением и убедившись, что не нужны живому процессу (см. рантайм-проверку в Шаге 0.5).

## ТРИВИАЛЬНЫЕ ФИКСЫ — ДЕЛАТЬ СРАЗУ (без вопроса)
Только то, что 100% не меняет поведение — по сути ОДИН безопасный автофикс:
- удаление неиспользуемых подключений библиотек: `ruff check --select F401 --fix <путь>` (ТОЛЬКО F401).
- НЕ автофиксить **F841** (неиспользуемые переменные): ruff его чинит лишь через `--unsafe-fixes`, может задеть логику → в ручной список группы B.
- `__pycache__/*.pyc` НЕ чистим как «фикс» на работающем сервисе — после смоук-рестарта регенерятся, толку ноль (пометить в группе E как фоновый хлам).
ПЕРЕД: бэкап (см. ниже). ПОСЛЕ: смоук-тест (бот импортируется/жив). В отчёте — простыми словами что сделал.
ВСЁ ОСТАЛЬНОЕ (удаление функций/мёртвого кода, слияние файлов, перенос, правка логики, удаление файлов-данных, снос `*.bak`) — только после явного «делай», по одному пункту.

## ШАГ 4 — ПРИМЕНЕНИЕ РИСКОВОГО (только по «делай», по одному)
1. БЭКАП до любой правки: если в папке git — СНАЧАЛА `git status`; если дерево ГРЯЗНОЕ (есть чужая незакоммиченная работа) — зафиксируй её ОТДЕЛЬНЫМ осмысленным коммитом (НЕ под именем «before cleaning», чтобы не смешать с уборкой), затем делай уборку отдельными коммитами по пунктам. Если git нет — `tar czf /path/to/backups/<proj>_<дата>.tgz <путь>` (для веток B/C — локально, где живёт код).
2. Правка маленьким обратимым шагом.
3. Смоук-тест ПО ВЕТКЕ (Шаг 0.5): A/VPS — `systemctl restart <svc>` → `is-active` + `journalctl -u <svc> -n 30 --no-pager`; B/локально — `py_compile` правленых файлов, живой процесс НЕ убивать, есть `/health` — пингани; C/гибрид — обе половины + проверка связки сквозным тестом. Для сайта — `curl -sI` адрес (200/301).
4. Сломалось → откат (git revert / распаковать бэкап) и стоп. Сообщи простыми словами.
5. Один пункт за раз, не пачкой.

## ЖЁСТКИЕ ЗАПРЕТЫ (правила пользователя)
- НЕ удалять/мержить файл, не прочитав его ЦЕЛИКОМ.
- НЕ перемещать файлы, «воткнутые» в сервис/nginx/cron — только КАРТА (переезд уронит сайт/бот).
- НЕ трогать рабочий бот в момент серии записей без `systemctl stop` (риск гонки), для разовой правки — можно на живом.
- Бэкап перед каждой правкой. Один шаг за раз. Стоп на первой поломке.
- Память пишем ТОЛЬКО на VPS (`/path/to/memory/`).
