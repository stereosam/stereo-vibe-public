# STEREO VIBE

STEREO VIBE is a one-click starter kit that turns a bare Windows or macOS machine into a
working AI-coding setup. It checks and installs Git, Node, Python and a coding-agent CLI
(Claude Code, Codex or Gemini), verifies whether you are signed in, checks which AI
services this network can actually reach, and then, if you agree, scaffolds the agent's
memory: a `CLAUDE.md` and a `memory/` folder pre-filled with what it just found out about
the machine.

What you see in `windows/` and `macos/` is exactly what is published as **StereoVibe
Lite** — the same files that are in the zip people download. The folders are generated by
a build script that also checks them (encodings, forbidden content, what may download what).

Also here: `engine/` and `commands/` — the write engine and the eleven slash commands that
the memory actually runs on. The kit scaffolds the files; these are what keeps them
honest. See [The engine and the commands](#the-engine-and-the-commands).

**Platforms:** Windows 10 (1809+) / 11 · macOS with Homebrew (see the limitations about macOS)
**Dependencies:** none. Two self-contained scripts — PowerShell 5.1 and bash 3.2.
**Note on language:** the console UX is Russian (the kit was built for a Russian-speaking
workshop). Identifiers, docs and commit messages are English. See "Reading the output".

---

## The problem

Every guide to agentic coding starts at "open your terminal and run the agent". The gap is
before that, and it is where people actually get stuck:

- the CLI is installed but not signed in — and an unauthenticated CLI looks exactly like a
  working one until it doesn't;
- Node is installed but not in this shell's `PATH`, so the check says "missing" and the
  person reinstalls what they already have;
- the package manager dies halfway through because the terminal is not elevated, and the
  only symptom is "it started installing and gave up";
- the AI services are closed for this network, and the failure mode is a timeout ten
  minutes later, not an error;
- and once the agent finally runs, it knows nothing about the machine it runs on.

STEREO VIBE is one pass that closes all five and ends with a verdict:
**TOOLS READY** (exit code 0) or **NOT READY** with the exact list of what is left.

## What it does, in order

1. **System** — free disk space, OS version.
2. **Tools** — Windows: WinGet (repaired if broken, see below), PowerShell 7, Git,
   Node.js LTS, Python, Telegram Desktop (only if you say yes).
   macOS: Homebrew (installed by its official installer if you say yes), Git, Node.js,
   Python, Telegram (only if you say yes).
3. **AI agents, your choice** — Codex CLI, Claude Code, Gemini CLI, and web versions of
   ChatGPT and Gemini as app shortcuts. Nothing is installed that you did not pick.
4. **Does it actually run** — Git, Node, npm, Python and pip are started for real, not
   just found on disk.
5. **Sign-in** — `codex login status`, `~/.claude/.credentials.json`,
   `~/.gemini/oauth_creds.json`, API keys in the environment. Read locally, sent nowhere.
6. **Reachability** — a real HTTPS request to `api.openai.com`, `api.anthropic.com`,
   `generativelanguage.googleapis.com`, `chatgpt.com` and `github.com`. A "this service is
   not available in your country" answer is recognised as closed, not as reachable.
7. **Verdict** — about the tools only. Whether AI services are reachable depends on the
   network, not on the computer, so it is reported separately.
8. **Project memory (opt-in)** — below.

## The part I would read first: it installs memory, not just tools

The installer has just found out everything an agent normally has to guess in its first
session: the OS and build, what is installed and at which version, which agent you are
signed into, which services are reachable from here. Instead of leaving that in a log, it
offers to write it into a project folder:

```
~/stereo-vibe/
├─ CLAUDE.md              rules the agent reads before touching anything
├─ memory/
│  ├─ infra_status.md     filled in from the checks that just ran — not a placeholder
│  ├─ PROJECT_status.md   current truth about the project (overwritten in place)
│  ├─ PROJECT_backlog.md  tasks: Active + Changelog
│  └─ PROJECT_history.md  append-only log, never edited retroactively
├─ scratch/               drafts — so they never land in the project
└─ backup/                backups — so they never land next to the original
```

A generated `infra_status.md` looks like this, with real values:

```markdown
## Machine
- OS: Windows 11 (build 26200)
- Free space on the system drive: 88.8 GB
- Projects live in: ~\stereo-vibe

## AI agents
| CLI | installed | signed in |
|---|---|---|
| Claude Code | 2.1.288 | yes |
| Codex | 0.146.1 | yes |
| Gemini CLI | 0.56.0 | no |

## Network reachability, measured at install time
| endpoint | reachable |
|---|---|
| api.anthropic.com | yes |
| generativelanguage.googleapis.com | yes |
```

Three memory files rather than one, because they have three different lifetimes:
**status is overwritten, history only grows, backlog lives in between.** The shape matters
more than the content — the agent knows where to look before it has read anything.

Nothing is ever overwritten: an existing file is left alone, and a second run writes
`infra_status.new.md` next to the old one instead of clobbering your edits. The file
deliberately contains **no machine name, no user name and no IP address**, and paths are
written relative to the home folder (`~\stereo-vibe`): it lives in the project, and
projects end up in git repositories, chats and screenshots.

`templates/` holds the rule set and the memory skeleton; each package carries a copy of it.
`CLAUDE.md` says: read before you touch, do not breed files, drafts to `scratch/`, backups
to `backup/`, and "think a tool is missing? read `memory/infra_status.md` first, then ask".
The Russian original is next to it as `CLAUDE.ru.md`; the installer picks by system
language.

## Install

Download and unpack, or clone. Nothing to build, nothing to configure, no keys.

**Windows**
```powershell
git clone https://github.com/stereosam/stereo-vibe-public
cd stereo-vibe-public\windows

# safe first run: checks only, installs nothing, asks for no rights
& ".\Запустить Vibe.cmd" /check

# full run: installs what is missing, asks for elevation via UAC
& ".\Запустить Vibe.cmd"
```

**macOS**
```bash
git clone https://github.com/stereosam/stereo-vibe-public
cd stereo-vibe-public/macos

bash "_не трогать/check-work-tools.sh" --check      # safe first run
open "Запустить Vibe.command"                       # full run
```

**Start with the check-only run.** The full run installs software: on Windows it
self-elevates through UAC and runs `winget install` / `npm install -g`; on macOS it runs
`brew install` and never uses `sudo` (Homebrew refuses to run as root).

The service folder is called `_не трогать` ("do not touch"): the people this was built for
open every folder they see, and that name works better than any README.

Flags — Windows: `-ReportOnly` (what `/check` passes), `-NoReport`, `-PreferredApps 1,2`,
`-ReportDir <dir>`, `-ProjectDir <dir>`. macOS: `--check`, `--no-report`, `--apps 1,2`,
`--report-dir <dir>`, `--project-dir <dir>`.

## Reading the output

The console is Russian. Every line starts with a status word:

| word | meaning |
|---|---|
| `ОК` | installed / works |
| `ПОСТАВЛЕНО` | installed during this run |
| `НУЖЕН ВХОД` | installed but not signed in |
| `ВНИМАНИЕ` | worth a look, not a blocker |
| `нет` | not selected — not a problem |
| `НЕТ` | missing — blocker |
| `ЗАКРЫТ` | closed from this network |
| `ОШИБКА` | the check itself failed |

The run ends with `ИНСТРУМЕНТЫ ГОТОВЫ` (tools ready, exit 0) or `СРЕДА НЕ ГОТОВА`
(not ready, exit 1) plus the list of blockers. A local log and a JSON report are written to
`%LOCALAPPDATA%\STEREO-Vibe-Lite\logs` on Windows and
`~/Library/Application Support/STEREO-Vibe-Lite/logs` on macOS. They stay on the machine.

## Network: what leaves the machine

Said plainly, because a kit like this should never surprise anyone:

- **Package installs** go to the official sources through winget, Homebrew and npm.
- **WinGet repair (Windows only).** If WinGet is missing or broken, the kit first
  re-registers the App Installer that is already in the system, without downloading.
  If that does not help, it asks, and only then downloads Microsoft's own packages from
  `github.com/microsoft/winget-cli/releases`, checks that every file carries a valid
  Microsoft Corporation signature, and installs nothing if one does not.
- **Version check.** At start it reads one field from
  `https://stereosam.ru/vibe-lite/version.json`. If a newer version exists, it prints a
  line saying where to get it. It downloads and executes nothing.
- **Anonymous summary — on by default.** After the check it sends one POST to
  `https://stereosam.ru/vibe-lite/report`: package version, a random install id, OS major
  version and build, admin yes/no, status/version/short code for each tool in the fixed
  list above, whether the AI services answered, the run duration. No user or machine name,
  no paths, no e-mail, no keys, no free text. That is how the workshop sees which steps
  break on real machines. **Turn it off with `-NoReport` / `--no-report`**: the summary is
  then only saved next to the log and no install id is created.

## Design decisions worth stealing

Each of these is a bug that reached a real person before it became a rule.

- **Presence-first.** Installed is green. Onboarding that fails on "you are one patch
  version behind" gets abandoned.
- **Every check is independent.** One failure adds a row; it never aborts the run. The
  report always has every line, which is what makes it useful to send to someone else.
- **Installed ≠ working.** Programs are started for real, and the sign-in gate is separate:
  an unauthenticated CLI reports a version number happily enough.
- **"Installed but not on PATH" is its own answer.** Known locations are probed before
  declaring something missing, so nobody is sent to install what they already have.
- **Every external call has a time limit and a visible heartbeat.** A silent installer is
  indistinguishable from a hung one, and people close the window. Package installs show a
  live bar; a program that does not answer its own `--version` within 30 s is reported as
  "did not answer", not as "missing" — otherwise the kit would reinstall it on top.
- **Exit codes are carried out of background jobs explicitly.** `exit N` inside a
  PowerShell job does not reach the caller; without a marker in the output, a failed
  `winget install` looked like a success.
- **No download-and-execute.** Nothing is fetched and run in memory; the only download
  path (WinGet repair) checks a Microsoft signature before installing. Antivirus software
  rightly treats "encoded PowerShell that downloads a script and runs it" as malware.
- **Quick-edit mode is switched off for the kit's console window.** A stray click in a
  classic console pauses the program until Enter is pressed, which looks exactly like a
  hang.
- **Launchers stay ASCII-only.** `cmd.exe` parses `.cmd` files in the OEM codepage; a
  Cyrillic character in an `echo` or `REM` breaks parsing outright. All localized text
  lives in the scripts.
- **A geo-block is not reachability.** From some countries the AI APIs answer 403 with
  "not supported in your country". A dropped connection and that answer are both "closed";
  401/405 from the service itself is "reachable".
- **Memory is never overwritten.** The installer writes files the agent will read, and the
  same rule it gives the agent applies to itself: an existing file is somebody's edit.

## The engine and the commands

The kit creates the memory. These two folders are what runs on it every day — the
same files, sanitised: server addresses, paths and ids replaced with placeholders,
nothing else changed.

### `engine/`

| | |
|---|---|
| `save_memory.py` | Writes a whole session back in one pass, from a JSON spec. Closes and adds backlog tasks, renumbers the gotcha list across all topic files and repairs duplicate numbers, splits the journal when the month rolls over, validates before it touches disk, writes atomically. Running it twice on the same spec changes nothing the second time. |
| `save_prep.py` | Read-only digest taken *before* writing: when memory was last saved, the tail of the journal, the highest gotcha number, the open tasks. Stops the agent from inventing an id that already exists. |
| `new_project.py` | Registers a new project: takes the lowest free number, creates `status` / `backlog` / `history` from templates, appends one line to the project map. Merged and retired numbers stay taken, so old references never point at the wrong project. |

Why an engine at all: an agent asked to "update the memory" will happily rewrite a
file it half-read. A spec plus an idempotent writer removes the whole class of
mistake — the agent describes *what changed*, and code decides *how it is written*.

### `commands/`

Eleven commands, written by hand and read by the agent as instructions:

| | |
|---|---|
| `go` | Start of a session: read the project's memory before doing anything, then wait for a task number |
| `save` | The write cycle above, end to end |
| `new` | Register a project |
| `tails` | What was left unfinished last time |
| `inbox` | Triage what arrived while I was away |
| `cleaning` | Periodic audit of a project: dead code, duplicates, leaked secrets, junk |
| `articles` | Park a topic worth writing about while it is still fresh |
| `newbot` | Create a Telegram bot without touching BotFather by hand |
| `golos` | Toggle spoken replies |
| `doit` | Switch from discussing to doing |
| `fleet` | The fleet dashboard |

Not every one of these will mean anything on your machine — `fleet` and `newbot`
describe my own infrastructure. They are here because a harness is not a tidy library:
it is the actual set of verbs one person uses, and the shape of that set is the honest
part.

## Roadmap

- Sign the Windows launcher, or wrap it in a small signed executable, to stop the
  SmartScreen warning on a freshly downloaded `.cmd`.
- Check quota and billing, not just the fact of a sign-in.
- English console UX behind a switch (the checks are language-agnostic already).
- One shared check definition instead of two hand-synced implementations.
- Write `infra_status` into a diff on every run, so an agent can see what changed on the
  machine since last time.

## Known limitations

- **The macOS version has not been run on a real Mac yet.** It passes `bash -n`,
  shellcheck and the build checks, and the memory step was tested in isolation; a run on
  actual hardware is pending. Treat it as a preview.
- **The console output is Russian.** The status table above maps it.
- **Two implementations, kept at parity by hand.** PowerShell and bash, no shared core.
- **No test suite.** Verification is a check-only run on a real machine.
- **The full run installs software.** Run the check-only mode first on any machine you
  care about.
- **The macOS launcher clears the quarantine attribute** on its own folder, otherwise
  Gatekeeper blocks a double-clicked `.command` downloaded from the internet. That is
  deliberate and visible in the launcher — read it before you run it.
- **Linux is not supported.**
- **The workshop version does more than this one.** Where AI services are unreachable it
  also helps the student get connected; that part is specific to a private service and is
  not published. What remains here is the diagnosis, which is the part that generalizes.
